# 開発手順書：食料管理＆レシピ提案アプリ

- **バージョン**: 0.1（ドラフト）
- **最終更新日**: 2026-04-18
- **前提ドキュメント**: [`requirements.md`](./requirements.md)

---

## 1. 開発方針

- **アジャイル／スプリント単位**（1スプリント = 2週間）で進行。
- **MVPファースト**：最小機能で早期にデプロイ、実利用フィードバックで改善。
- **垂直スライス**：UI〜DBまで細く一気通貫で実装し、継続的に太らせる。
- **CI/CD導入を初期から**：Vercel（or Cloudflare Pages）+ GitHub Actions。

---

## 2. フェーズ構成

| フェーズ | 期間目安 | ゴール |
|---------|---------|--------|
| Phase 0: 準備 | 1週間 | 技術選定・環境構築・CI/CD整備 |
| Phase 1: MVP | 4〜6週間 | 手入力在庫管理 + AIレシピ提案 + 手動調理記録 |
| Phase 2: β | 3〜4週間 | レシートOCR対応 + カレンダーUI + PWA化 |
| Phase 3: v1.0 | 2〜3週間 | 在庫自動減算 + お気に入り + 買い物リスト + 統計 |
| Phase 4: 運用 | 継続 | 改善・機能拡張・コスト最適化 |

> 1人フルタイム想定で約 **3〜4ヶ月**。副業ペース（週10h）なら **6〜9ヶ月**。

## 4. 推奨ブランチ戦略

- `main`: 本番反映ブランチ（タグでリリース管理）
- `develop`: 次回リリース候補統合先
- `feature/<短い説明>`: 機能開発
- `fix/<短い説明>`: 不具合修正
- `docs/<短い説明>`: ドキュメントのみ

PRテンプレに「関連Issue」「スクショ」「テスト観点」を必須化。

## 5. 品質保証

| 種別 | ツール | 対象 |
|------|--------|------|
| 静的解析 | TypeScript + ESLint | 全コード |
| フォーマット | Prettier | 全コード |
| 単体テスト | Vitest | ロジック層 |
| コンポーネントテスト | React Testing Library | 主要UI |
| E2E | Playwright | ハッピーパス + 代表導線 |
| 型安全 DB | Prisma / Drizzle | クエリ |
| スキーマ検証 | Zod | API境界・LLM出力 |

LLM出力は **必ず Zod で検証** し、失敗時は再試行／フォールバックを実装。

## 6. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| LLMコスト暴発 | 運用費超過 | キャッシュ、Haiku活用、レート制限、月次アラート |
| OCR精度不足 | UX悪化 | LLMで補正、ユーザー確認必須、店舗別テンプレ |
| LLMのハルシネーション | 誤った材料・手順 | Zod検証、出力スキーマ固定、ユーザー確認UI |
| 個人情報流出 | 信用失墜 | PII マスキング、最小保持、暗号化 |
| 外部API障害 | 機能停止 | 抽象化層、プロバイダ切替可能に、縮退運転 |
| 1人開発の属人化 | 開発停滞 | ドキュメント整備、PRレビュー（AIレビュー活用） |
